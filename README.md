# ParallelSchedulingSolver

Research code for parallel scheduling problems.

## Compilation

```shell
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel && cmake --install build --config Release --prefix install
```

Setup Python environment to use the Python scripts:
```shell
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Download data files:
```shell
python scripts/download_data.py
```

Run:
```shell
./install/bin/parallelschedulingsolver  --verbosity-level 1  --input ./data/tests/total_flow_time_parallel/tft_n3x3_s0.json  --algorithm assignment-total-flow-time  --certificate solution.json
```

Visualize solution:
```shell
python scripts/visualize.py solution.json
```

## Implemented algorithms

Each algorithm has a page in [`doc/`](doc/) describing it, the problems it supports, the cases in which it is optimal and its guarantees. When an algorithm detects that the instance is one of the special cases in which it is optimal, it sets the bound to the value of its solution and the output reports `"Optimal": true`.

| Algorithm | Option | Optimal for |
| --- | --- | --- |
| [Greedy, longest processing time first (LPT)](doc/greedy_longest_processing_time.md) | `--algorithm greedy-longest-processing-time` | $1 \mid\mid C_{\max}$; $P \mid\mid C_{\max}$ if $n \le m + 1$, or if an optimal schedule has at most two jobs per machine, or if $p_j = p$. $\frac{4}{3} - \frac{1}{3m}$ approximation for $P \mid\mid C_{\max}$ |
| [Greedy, weighted shortest processing time first (WSPT)](doc/greedy_shortest_processing_time.md) | `--algorithm greedy-shortest-processing-time` | $1 \mid\mid \sum w_j C_j$; $P \mid\mid \sum C_j$; $1 \mid\mid \sum w_j T_j$ if all jobs are tardy |
| [Greedy, earliest due date first (EDD)](doc/greedy_earliest_due_date.md) | `--algorithm greedy-earliest-due-date` | $1 \mid\mid L_{\max}$; $P \mid p_j = p \mid L_{\max}$; $1 \mid\mid \sum T_j$ if at most one job is tardy or due dates are agreeable |
| [Moore-Hodgson](doc/moore_hodgson.md) | `--algorithm moore-hodgson` | $1 \mid\mid \sum U_j$ |
| [Assignment, total flow time](doc/assignment_total_flow_time.md) | `--algorithm assignment-total-flow-time` | $R \mid\mid \sum C_j$ |

## Tests

Build and run the unit tests:
```shell
cmake --build build --config Release --parallel
ctest --test-dir build/test --output-on-failure
```

There are two kinds of tests in `test/algorithms/`:
* exact schedules returned on small hand-written instances (`ScheduleTest`);
* optimal values on the generated test instances (`ExactAlgorithmTest`). Each `<algorithm>_test.txt` file lists instances and their optimal value. When the algorithm proves optimality on these instances, the test also checks its bound.

The test instances are generated by `scripts/generate_data.py`. The reference values are computed by `scripts/solve_test_data.py`, either by brute force on the small instances or by running an algorithm that proves optimality, for example:
```shell
python3 scripts/solve_test_data.py --criterion total-flow-time --instances data/test_tft_single.txt data/test_tft_parallel.txt --output test/algorithms/assignment_total_flow_time_test.txt
python3 scripts/solve_test_data.py --algorithm assignment-total-flow-time --instances data/test_tft_parallel.txt --output tft_parallel.txt
```
