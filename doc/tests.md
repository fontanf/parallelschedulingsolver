# Tests

## Running the tests

Download the test instances (the `tests` archive of the data, see `data/data.json`):
```shell
python3 scripts/download_data.py --archives tests
```

Build and run the tests:
```shell
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DPARALLELSCHEDULINGSOLVER_USE_HIGHS=ON
cmake --build build --config Release --parallel
ctest --test-dir build/test --build-config Release --parallel --output-on-failure
```

The tests of the MILP algorithms are only built with an MILP solver (`-DPARALLELSCHEDULINGSOLVER_USE_HIGHS=ON`). The tests run from the root of the repository, which contains `data/` and `test/`.

To run the tests of one algorithm, filter them by name with `-R`:
```shell
ctest --test-dir build/test -R MilpTimeIndexed --output-on-failure
```

or run the test executable directly, with a gtest filter, to see the output of the algorithm:
```shell
./build/test/algorithms/ParallelSchedulingSolver_milp_time_indexed_test --gtest_filter='*ReleaseDates*'
```

The CI (`.github/workflows/build.yml`) downloads the `tests` archive, builds with HiGHS and runs all the tests on Linux, macOS and Windows.

## Test instances

The test instances are generated by `scripts/generate_data.py`, in `data/tests/<objective>_<family>/`, and listed in `data/test_<objective>_<family>.txt`. An instance `tft_n3x5_s0` has 3 machines, 5 jobs per machine (15 jobs) and seed 0.

The families are:
* `single`: one machine;
* `single_release_dates`: one machine, with release dates;
* `identical`: identical parallel machines;
* `identical_equal_processing_times`: identical parallel machines, all the jobs with the same processing time;
* `unrelated`: unrelated parallel machines;
* `single_setup_times`, `single_release_dates_setup_times`, `identical_setup_times`, `unrelated_setup_times`: the same with sequence-dependent setup times, including the setup times of the first job of each machine, drawn in $[0, 20]$ for processing times in $[1, 100]$ (the same on all the machines for `identical_setup_times`).

Due dates follow the tardiness factor / range of due dates scheme of Potts and Van Wassenhove (1985), so they don't depend on the processing times.

The instances are published in a GitHub release. To change them, regenerate them, publish a new archive with `scripts/create_data_archives.py`, and update `data/data.json`.

## Writing tests

The tests of an algorithm are in `test/algorithms/<algorithm>_test.cpp`, with the helpers of `test/algorithms/tests.hpp`, and are declared in `test/algorithms/CMakeLists.txt`. There are two kinds of tests.

### Exact schedules: `ScheduleTest`

On a small instance written in the test, check the schedule returned by the algorithm: for each machine, the sequence of (job id, start time), the objective value, and whether the algorithm proves optimality (its bound equals the value of its solution).

```cpp
INSTANTIATE_TEST_SUITE_P(
        GreedyLongestProcessingTime,
        ScheduleTest,
        testing::ValuesIn(std::vector<ScheduleTestParams>{
            {
                // Order: 1 (5), 3 (4), 2 (3), 0 (2), 4 (1).
                // Job 4 completes at 8 on both machines; ties go to the first
                // machine.
                "IdenticalMachines",
                // Algorithm.
                [](const Instance& instance) { return greedy_longest_processing_time(instance); },
                // Objective and number of machines.
                Objective::Makespan,
                2,
                // Jobs: {processing times on each machine, release date, due date, weight}.
                {{{2, 2}}, {{5, 5}}, {{3, 3}}, {{4, 4}}, {{1, 1}}},
                // Expected schedule: for each machine, (job id, start time).
                {{{1, 0}, {0, 5}, {4, 7}}, {{3, 0}, {2, 4}}},
                // Expected objective value.
                8,
                // Expected proof of optimality: omitted, false by default.
            },
        }),
        schedule_test_name);
```

Use them for:
* the greedy algorithms, whose solution is fully determined by their rule (tie breaking included);
* the special cases of an exact algorithm (idle time, release dates, jobs without due date...), with an instance whose optimal schedule is unique: write in a comment why it is.

### Optimal values: `ExactAlgorithmTest`

On the generated test instances, check that the algorithm finds the optimal value, and, if it proves optimality, that its bound is the optimal value. The instances and their optimal values are listed in `test/algorithms/<algorithm>_test.txt` (`<instance path> <optimal value>`, the path relative to `data/`). Add the file to the sources of the test executable in `test/algorithms/CMakeLists.txt`.

```cpp
INSTANTIATE_TEST_SUITE_P(
        MilpTimeIndexed,
        ExactAlgorithmTest,
        testing::ValuesIn(get_test_params(
                // One or several algorithms (e.g. several parameter settings),
                // each run on all the instances.
                {
                    [](const Instance& instance) { return milp_time_indexed_test(instance, true); },
                    [](const Instance& instance) { return milp_time_indexed_test(instance, false); },
                },
                {
                    get_test_instance_paths(get_path({"test", "algorithms", "milp_time_indexed_test.txt"})),
                },
                // Criterion compared to the reference value (default: the objective value).
                [](const Solution& solution) { return solution.objective_value(); },
                // Bound compared to the reference value (omit it if the
                // algorithm doesn't prove optimality).
                [](const Output& output) { return output.bound(); })),
        exact_algorithm_test_name);
```

The criterion may differ from the objective of the instances. For example, EDD is optimal for the maximum lateness, so its tests run on the total tardiness instances and compare `solution.maximum_lateness()` and `output.maximum_lateness_bound` to the optimal maximum lateness.

An algorithm that optimizes the objective of the instance can be tested on another objective by building a copy of the instance with this objective (see `maximum_lateness_instance` in `test/algorithms/milp_assignment_test.cpp`). The solution of the output refers to its instance, so the copy must outlive the test: keep it in a static container.

Use them only for algorithms that are optimal on the listed instances: exact algorithms, and the other algorithms on the special cases where they are optimal (e.g. LPT on one machine, SPT for $P \mid\mid \sum C_j$).

### Heuristic algorithms

The solution of a local search or of another randomized heuristic can't be predicted, so `ScheduleTest` doesn't apply to them. They are tested with `ExactAlgorithmTest` too, without the bound criterion: on instances small enough for the heuristic to always find an optimal solution quickly, check that it finds the optimal value. The criterion for choosing the instances is their size, not the time an exact algorithm needs to solve them. Fix the seed of the random generator in the test, so that a failure can be reproduced.

For example, `test/algorithms/local_search_test.cpp` checks that the local search finds the optimal value of the total flow time and total tardiness test instances (up to 25 jobs) with seed 0.

## Reference values

The optimal values of the `.txt` files are computed by `scripts/solve_test_data.py`, never by the tested algorithm itself, with one of two methods:
* brute force (`--criterion <criterion>`, or `--criterion objective` for the objective of each instance): the script runs the [brute force algorithm](brute_force.md) (`--algorithm brute-force`) on a copy of the instance whose objective is the criterion. For `number-of-on-time-jobs`, the copy is a throughput instance with unit weights. The brute force enumerates all the sequences of all the machines, or, on parallel machines without setup times, all the assignments with an optimal sequencing rule when there is one. Instances with more than `--maximum-number-of-candidates` candidates (default $10^6$) are skipped.
* an algorithm that proves optimality (`--algorithm <algorithm>`), on the special cases where it is exact. For example, `assignment-total-flow-time` is exact for $R \mid\mid \sum C_j$ in polynomial time, so it gives the optimal values of instances too large for brute force, to test other algorithms on the same problem. Only the instances on which the algorithm reports `"Optimal": true` are written.

The brute force is simple enough for its correctness to be easy to trust. Its own reference values come from other exact algorithms: the ones proved by the time-indexed MILP, kept with `--keep-if-solved-by brute-force` on the instances small enough for the brute force (`brute_force_test.txt`).

The tests must stay fast: the instances of the tests of an exact algorithm whose running time grows quickly with the size of the instances should be solved in less than 1 s. `--keep-if-solved-by <algorithm>` only keeps the instances on which this algorithm proves optimality within `--time-limit`, for each set of arguments given with `--keep-if-solved-with`. The script fails if the algorithm proves a value different from the reference.

The commands that generate the `.txt` files of the repository:
```shell
python3 scripts/solve_test_data.py --criterion makespan --output test/algorithms/greedy_longest_processing_time_test.txt --instances \
    data/test_makespan_single.txt \
    data/test_makespan_identical_equal_processing_times.txt
python3 scripts/solve_test_data.py --criterion total-flow-time --output test/algorithms/greedy_shortest_processing_time_test.txt --instances \
    data/test_tft_single.txt \
    data/test_twft_single.txt \
    data/test_tft_identical.txt \
    data/test_tft_identical_equal_processing_times.txt
python3 scripts/solve_test_data.py --criterion maximum-lateness --output test/algorithms/greedy_earliest_due_date_test.txt --instances \
    data/test_tt_single.txt \
    data/test_twt_single.txt \
    data/test_tt_identical_equal_processing_times.txt \
    data/test_twt_identical_equal_processing_times.txt
python3 scripts/solve_test_data.py --criterion number-of-on-time-jobs --output test/algorithms/moore_hodgson_test.txt --instances \
    data/test_tt_single.txt \
    data/test_tft_single.txt \

    data/test_tft_single.txt \
    data/test_tft_identical.txt \
    data/test_tft_identical_equal_processing_times.txt \
    data/test_tft_unrelated.txt
python3 scripts/solve_test_data.py --criterion objective --output test/algorithms/milp_time_indexed_test.txt \
    --keep-if-solved-by milp-time-indexed --time-limit 0.5 \
    "--keep-if-solved-with=--normal-instants 1" "--keep-if-solved-with=--normal-instants 0" \
    --instances data/test_*_{single,single_release_dates,identical,identical_equal_processing_times,unrelated}.txt
python3 scripts/solve_test_data.py --criterion makespan --output test/algorithms/milp_assignment_makespan_test.txt --instances \

python3 scripts/solve_test_data.py --criterion maximum-lateness --output test/algorithms/milp_assignment_maximum_lateness_test.txt --instances \
    data/test_tt_single.txt \
    data/test_tt_identical.txt \
    data/test_tt_identical_equal_processing_times.txt \
    data/test_tt_unrelated.txt
python3 scripts/solve_test_data.py --criterion objective --output test/algorithms/milp_positional_test.txt \
    --keep-if-solved-by milp-positional --time-limit 0.5 \
    --instances data/test_*_{single,single_release_dates,identical,identical_equal_processing_times,unrelated}.txt
python3 scripts/solve_test_data.py --criterion objective --output test/algorithms/local_search_test.txt --instances \
    data/test_{tft,twft,tt,twt}_{single,single_release_dates,identical,identical_equal_processing_times,unrelated}.txt
python3 scripts/solve_test_data.py --criterion objective --output test/algorithms/local_search_setup_times_test.txt --instances \
    data/test_{tft,twft,tt,twt}_*setup_times.txt
python3 scripts/solve_test_data.py --criterion objective --output test/algorithms/successive_sublimation_dynamic_programming_test.txt --instances \
    data/test_{tft,twft,tt,twt}_{single,single_setup_times}.txt
python3 scripts/solve_test_data.py --algorithm milp-time-indexed --time-limit 1 --output test/algorithms/brute_force_test.txt \
    --keep-if-solved-by brute-force "--keep-if-solved-with=--maximum-number-of-candidates 100000" \
    --instances data/test_*_{single,single_release_dates,identical,identical_equal_processing_times,unrelated}.txt
python3 scripts/solve_test_data.py --algorithm milp-time-indexed --time-limit 10 --output test/algorithms/local_search_parallel_tardiness_test.txt --instances \
    data/test_tt_identical.txt \
    data/test_tt_identical_equal_processing_times.txt \
```

The reference values of `local_search_parallel_tardiness_test.txt` are the ones proved by the time-indexed MILP, on the total tardiness instances on parallel machines, including the ones too large for brute force.

For example, to get the optimal values of all the unrelated machines total flow time instances, including the ones too large to enumerate:
```shell
python3 scripts/solve_test_data.py --algorithm assignment-total-flow-time --instances data/test_tft_unrelated.txt --output tft_unrelated.txt
```

The commands need the solver built and installed in `install/` (`cmake --install build --config Release --prefix install`), with HiGHS for the MILP algorithms.

## Before adding an algorithm

Besides the unit tests, compare the algorithm with the references on all the test instances, including the ones too large for the tests, and with the other exact algorithms of the repository on the same problems: a wrong bound or a wrong proof of optimality is more likely on instances where the solver branches.
